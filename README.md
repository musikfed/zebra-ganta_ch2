# Zebra Ganta · Chapter 2 · HDD Laboratory

**PEGINELAB / Grep Pipe — Гантова зебра. Часть 2. Цена перемещения**

**Независимое исследование без обещаний и гарантий ускорения.** Программа изучает чтение на настоящем физическом 2,5-дюймовом HDD HGST (Disk 2), а не на симуляторе. Отдельные поздние модели являются *симуляцией* и не равны лабораторным замерам. Результаты могут подтвердить, не подтвердить или опровергнуть гипотезу. Это не готовый оптимизатор HDD и не доказательство повышения производительности.

## Испытательный стенд № 001

- Контроллер: ноутбук Acer Swift 3 SF314-41; Ryzen 5 3500U, 20 ГБ RAM, Windows 11 Pro.
- Два SSD ноутбука **не участвуют** в испытаниях: AMD R5SL120G (Disk 0), SK hynix HFM512GDJTNG-8310A (Disk 1).
- Образец: **HGST HTS725050B7E630**, 500 106 780 160 байт (Get-Disk); 500 105 249 280 байт (Win32_DiskDrive), Windows **Disk 2**, USB–SATA JMicron, NTFS **T:**.
- Раздел T: начинается с 16 777 216 байт; размер кластера NTFS — 4096 байт.
- Данные Windows до опыта: 335 ч наработки; 6071 циклов парковки; 986 запусков/остановок; температура 29 °C.
- Полный ATA SMART через текущий USB-мост не получен: smartctl возвращает `IOCTL_SCSI_PASS_THROUGH ... Error=5`. Состояние поверхности не подтверждено.
- Показание Windows «физический сектор 512 Б» может отражать особенности USB-моста; **не выдавайте его за подтверждённую физическую геометрию**.

## Старт на Acer Swift 3 — Windows 11 Pro, F:\, uv 0.11.15

Рабочий каталог проекта — **F:\zebra-ganta_ch2**. Результаты опыта сохраняются в **F:\zebra-ganta_ch2\results**, никогда на испытываемом HGST **T:**. На компьютере пользователя уже имеются Python 3.14.4 / 3.13.13 / 3.12.9 и uv 0.11.15.

Первоначальная установка в PowerShell:

```powershell
Set-Location F:\
git clone https://github.com/musikfed/zebra-ganta_ch2.git
Set-Location F:\zebra-ganta_ch2
uv sync --python 3.14.4
uv run python lab.py inspect
uv run python -m unittest discover -s tests -v
```

При повторном использовании (если репозиторий уже существует):

```powershell
Set-Location F:\zebra-ganta_ch2
git pull --ff-only
uv sync --python 3.14.4
uv run python lab.py inspect
```

`uv sync` создаёт или обновляет локальное **F:\zebra-ganta_ch2\.venv**, а `uv run` запускает команды через это окружение, без ручного `Activate.ps1`. Сторонних зависимостей у текущего лабораторного инструмента нет. `uv.lock` фиксируется в Git после первого `uv lock` или `uv sync` на рабочей станции.

**Измерения выполняются нативно в Windows**, а не в WSL: скрипт использует `Get-Disk`, Windows CIM и `\\.\PhysicalDrive2`. WSL подходит для разработки, документации и анализа полученных CSV, но не является прямой заменой нативного доступа к USB–SATA устройству. Результаты из WSL могут иметь другие задержки из-за виртуализованного стека I/O.

Проверьте, что вывод `inspect` показывает именно HGST, Disk 2, USB и несистемное устройство. **Windows сообщает две различающиеся ёмкости**: `Get-Disk.Size = 500106780160` и `Win32_DiskDrive.Size = 500105249280`. Эти значения зафиксированы раздельно; приложение сверяет оба с наблюдениями стенда, а не подменяет их предполагаемой заводской ёмкостью. При новом расхождении опыт будет остановлен. Затем откройте PowerShell **от имени администратора**, перейдите в `F:\zebra-ganta_ch2` и запустите **одной строкой**:

```powershell
uv run python lab.py scan --disk 2 --expect-model HTS725050B7E630 --expect-size 500106780160 --samples 5 --mib 16 --repeats 3
```

Команда проверит модель, размер, статус System/Boot и право на открытие устройства; запросит явное подтверждение по фразе `READ HGST DISK 2`. **Вводите фразу только после проверки паспорта на экране.**

Если Windows запретит чтение физического устройства, программа завершится с ошибкой, не перейдёт автоматически к другому диску и не попытается изменять защиту тома. Не размонтируйте диск автоматически и не отключайте защиту Windows.

Выходные данные (после успешного чтения): `results\<UTC_TIMESTAMP>\manifest.json`, `measurements.csv`, `summary.csv` и `speed.svg`. В Git результаты не попадают автоматически: каталог `results/` исключён через .gitignore. Публикация обезличенных измерений выполняется осознанно и отдельно.

## Что делает опыт 001

1. Читает сведения о физическом диске с помощью PowerShell/CIM.
2. Сверяет номер, точную модель и ёмкость, отклоняет системный/загрузочный диск и любое несовпадение.
3. Открывает `\\.\PhysicalDriveN` только через `os.O_RDONLY`.
4. В нескольких зонах адресного пространства читает ограниченные блоки и измеряет время `perf_counter_ns`.
5. Сохраняет `manifest.json`, `measurements.csv`, `summary.csv` и статический `speed.svg`.

**Ограничения:** буферизация ОС/USB-моста не отключена; сырые наблюдаемые скорости **не являются чистой скоростью магнитной поверхности**. Для проверки повторяемости используйте различные порядки точек, учитывайте нагрев и отдельные контрольные серии с прямым SATA. Этот этап не измеряет достоверно время позиционирования головки и не устанавливает физическую карту дорожек.

- **002** — 21 зона LBA × 3 повтора: проведено, 63 измерения сохранены.
- **003** — **глава 3 «Цена одного перехода»**: натуральные опыты на физическом 2,5-дюймовом HDD, 20 + 20 + 40 пар; 59 из 80 дальних целевых чтений были медленнее близких, 21 — быстрее. Медианы попарных разниц 9,2222 / 9,0640 / 9,6610 мс. См. `docs/experiments/003-near-far-hgst-2026-11-12.md` и `data/observed/exp003_near_far_paired_analysis_2026-11-12.csv`. Полные оригинальные `observations.csv` остаются локально на Acer до импорта.

- **005** — **главы 7–8**: контроль условий, анализ повторяемости, проверка гипотез, документирование отрицательных результатов.

### Глава 3: проведённые опыты и анализ оригинальных CSV

**Важно:** ошибка `can't open file 'F:\\zebra-ganta_ch2\\analyze_transitions.py'` означает, что локальная копия ещё не получила новый файл из GitHub. Первым делом сделать `git pull --ff-only` и проверить `Test-Path .\\analyze_transitions.py`. Не нужно повторно запускать измерение ради появления анализатора. Каждую команду PowerShell выполнять **отдельно**:

```powershell
Set-Location F:\zebra-ganta_ch2
git pull --ff-only
uv sync --python 3.14.4
Test-Path .\analyze_transitions.py
uv run python -m unittest discover -s tests -v
uv run python analyze_transitions.py results\20261112T185114Z-transitions\observations.csv results\20261112T185549Z-transitions\observations.csv results\20261112T185935Z-transitions\observations.csv
```

Три серии чтения уже выполнены. Сейчас выполняется **только анализ файлов** и никаких подтверждений `READ HGST DISK 2` не требуется. Если `Test-Path` вернул `False`, остановиться и проверить, что `git pull` действительно обновил ветку `main`. Первичные `observations.csv` и `manifest.json` в `F:\zebra-ganta_ch2\results\<UTC_TIMESTAMP>-transitions\` не удалять.

Тест выполняет по две альтернативы (`near` и `far`) на каждой паре, с контрольным чтением общего опорного LBA перед каждым измерением. Непосредственно измеряется время **чтения 4-КиБ блока через Windows + USB**, а не механический seek. Проведены 20, 20 и 40 пар (всего 80 пар; 160 целевых + 160 опорных чтений по 4 КиБ). Для корректного анализа нужны все три оригинальных CSV. Разница медиан из консоли: 6,1920; 6,1618; 8,1186 мс. Эти числа нельзя считать изолированным временем перемещения головок.

Если сравнение не покажет преимуществ дальнего/ближнего доступа или значения будут подозрительно малы из-за кэша — это допустимый результат, а не повод подгонять параметры. При отсутствии допуска Windows программа завершится с ошибкой и не будет обходить защиту.

## Сравнение с документацией изготовителя и вопрос USB

[HGST Travelstar Z7K500.B — первоисточники, паспорт и честное сравнение с USB-опытами](docs/experiments/hgst-manufacturer-vs-usb-lab.md).

По официальному HGST/Western Digital: SATA 6 Гбит/с, до **163 МБ/с** последовательной передачи **у внешнего диаметра (OD)**, 12 мс типовой средний поиск при чтении без командных накладных расходов, 7200 об/мин, 32 МБ буфер. В наших физических опытах через USB–SATA наблюдается в основном около 37–38 МБ/с. **Нельзя автоматически приписать различие USB**: фактическая скорость соединения моста не измерена; два исправных хост-контроллера AMD USB 3.10 этого не подтверждают. Дальше требуется проверка конкретного подключения через Microsoft USBView и, при возможности, контроль с другим адаптером/прямым SATA.

## Безопасность

Исходный код не выполняет операций записи, форматирования, изменения таблицы разделов или SMART self-test. Чтение изношенного HDD тоже может проявить существующую неисправность: не используйте единственную копию ценных данных. Режим по умолчанию ограничен несколькими небольшими областями, а не сплошным полным сканированием 500 ГБ.

## Проверка Windows SDK после установки на Acer

В `tools/windows-sdk-doctor.ps1` находится SDK Doctor v5. После установки Windows SDK сначала обновите локальную копию, **затем** запускайте проверку (команды по порядку):

```powershell
Set-Location F:\zebra-ganta_ch2
git pull --ff-only origin main
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\tools\windows-sdk-doctor.ps1
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\tools\windows-sdk-doctor.ps1 -BuildTest
```

Обычная проверка не меняет систему; `-BuildTest` дополнительно создаёт временный минимальный исходник C, компилирует его через `VsDevCmd.bat` + MSVC + WinAPI, запускает EXE и удаляет временные файлы. **Это не испытание HGST**, не чтение `\\.\PhysicalDrive2`, не запись на `T:` и не доказательство ускорения HDD. Если SDK ещё не предоставил `Windows.h` и `kernel32.lib`, тест сборки пропускается. Все результаты лабораторных экспериментов из `results/` сохраняются.
