# Этап 007Б — подготовка тестового корпуса для «Гантовой зебры»

**СТАТУС: ТОЛЬКО ПЛАН, запись запрещена.** Протокол 007 (чтение метаданных NTFS) сохраняется; 008 (механика и ресурс) не переименовывается. Этот этап добавлен между ними для подготовки будущего разрешённого опыта. [English version](007b-corpus-preparation.en.md).

## Зачем нужен корпус

На HGST T: обычных доступных файлов не обнаружено, поэтому реальную карту файловых экстентов пока нечего измерять. В опытах №004–005 также выявлена существенная зависимость повторных обращений от кэша. Для сравнения обычной файловой раскладки и Adaptive Macro Interleave нужно сначала обеспечить одинаковый набор полезных данных и зафиксировать действительно получившиеся экстенты.

## Проект данных

| Вариант | Файлов | Размер одного | Полезный объём |
|---|---:|---:|---:|
| Один крупный файл | 1 | 1 ГиБ | 1 ГиБ |
| Набор мелких файлов | 4096 | 256 КиБ | 1 ГиБ |
| Архив набора | 1 | Зависит от архиватора/сжатия | Исходные 1 ГиБ; фактический архив измерить отдельно |

Сопоставление архива и набора мелких файлов не заменяет сравнение их размещения: сжатие и накладные расходы архиватора измеряются независимо. Для предварительного планирования заложен осторожный бюджет **4 ГиБ свободного места** на выделенном тестовом накопителе; это не автоматически гарантированный предел, поскольку выделенные на ФС блоки, метаданные и промежуточные файлы могут увеличить затраты.

## Безопасность

**Никакого автоматического создания, удаления, перезаписи, форматирования или перемещения файлов на HGST T:.** Рабочий HDD исследуется в read-only режиме. Для реального опыта создания тестовых объектов потребуется отдельное письменное разрешение оператора на специально выбранный расходный тестовый носитель, проверка идентификаторов диска/тома, отсутствие полезных данных, резервная копия и контроль пути назначения. Результаты анализа будут сохраняться вне экспериментального тома.

Подготовлен `tools/plan_corpus007b.py`: **чистый расчёт**, не читает даже свободное место тома. Выводит два основных варианта по 1 ГиБ, необязательный архив, ориентир места, будущие ограничения и явные признаки `target_approved_for_writes=false`, `generator_implemented=false`. Даже если указать `--target hgst-t`, разрешение записи не появляется: это лишь текстовая метка в отчёте.

```powershell
git pull --ff-only origin main
uv run python tools/plan_corpus007b.py
uv run python tools/plan_corpus007b.py --target hgst-t
uv run python -m unittest discover -s tests -v
```

Все четыре команды не должны создавать тестовые файлы на HDD. Последняя запускает локальные тесты Python; **результат Windows ещё предстоит получить**.

## Что понадобится для настоящего опыта

До любой записи: выделенный расходный носитель и паспорт его идентификаторов; фактическая свободная ёмкость; резервная копия; подтверждение путей; шаблоны содержимого с неповторяющимися блоками; контрольные SHA-256; разделение времени создания, архивации, чтения и очистки; случайно сбалансированный порядок сравнений; холодные/повторные чтения; карты экстентов до и после размещения; несколько независимых прогонов.

**Необходимое условие проверки алгоритма:** не достаточно переименовать файлы «baseline» и «Zebra». Должны существовать и быть проверены **две реальные, различающиеся раскладки**; иначе можно проверять только характеристики обычной NTFS, но нельзя утверждать пользу Adaptive Macro Interleave.

Вывод: этап 007Б готовит протокол, но **не выполняет эксперимент и не создаёт никаких магнитных островков**.
