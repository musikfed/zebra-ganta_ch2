# Эксперимент №008 — накопленная цена переходов LBA

**Статус 13.11.2026: код предложен, реальных замеров №008 ещё нет.** Это практическое продолжение №003 «Цена одного перехода». Ранее запланированная тема 008 «Механика, торможение и ресурс» сохраняется как теоретический раздел общего протокола 006–008. Измерения движения головки, угла или износа по USB невозможны.

## Метод

Три режима: sequential (по возрастанию адресов), alternating (чередование нижнего и верхнего края адресного диапазона), shuffled (детерминированное перемешивание). Каждый обрабатывает равный объём: 8 зон × 16 адресов × 4096 байт. Проводим три раунда с циклическим сдвигом порядка режимов; суммарно 1152 чтения / 4,5 МиБ. Ни один LBA в этом плане не повторяется: режимы используют непересекающиеся адреса из сопоставимых областей диска. Поэтому изучаем не строго одинаковые блоки, а сравнимые выборки из одних и тех же регионов. При необходимости уменьшаем выборку до 8 или увеличиваем до 32 чтений на зону.

Цель: сравнить накопленную задержку и MB/s при последовательной и разбросанной траектории обращений к LBA. Сумма LBA-дистанций — **логический показатель**, а не физическая длина пути головки. Запуск режимов один за другим; никакой одновременной многопоточности.

## Инструкция для Acer, безопасная проверка без дисковых операций

После внесения изменений в main и обновления локальной копии:

~~~powershell
Set-Location F:\zebra-ganta_ch2
git pull --ff-only origin main
uv run python -m unittest discover -s tests -v
uv run python experiment008.py
~~~

По умолчанию только PLAN ONLY: ни физический диск, ни файлы, ни PnP не опрашиваются. План должен указать 3 раунда, 3 режима и 1152 уникальных смещения. Если план или тесты упали — реальный опыт не запускать.

## Настоящий read-only тест, только после проверки

При сохранении конфигурации HGST HTS725050B7E630, Windows Disk 2 / T:, ORICO VIA USB 2109:0715, SuperSpeed и каталога проекта на F:, в PowerShell с правами администратора:

~~~powershell
Set-Location F:\zebra-ganta_ch2
uv run python experiment008.py --run
~~~

Перед чтением программа сверяет модель, оба размера диска, статус диска, NTFS T:, PnP-предка VIA Labs, что F: не принадлежит Disk 2, и повторяет проверки после подтверждения. Требуется точная фраза READ HGST DISK 2 EXP008. Открытие только в режиме rb без буферизации Python. При ошибке **нет** попытки переключиться на D:, обойти права или изменить настройки Windows. Результаты только на F:\zebra-ganta_ch2\results. На T: ничего не записывается, не создаётся и не перемещается.

## Результат и ограничения

Сохраняются manifest.json, observations.csv, summary.csv. Для каждого чтения: номер раунда и профиля, смещение, зона, расстояние до предыдущего LBA, задержка. Для профиля: полное время, MB/s, p50/p95/p99 задержек, число чтений менее 1 мс, сумма логических дистанций и процент отличия от последовательного режима соответствующего раунда. При частичной ошибке сохраняются observations_partial.csv и error.txt, статус остаётся incomplete.

Опыт №005 показал, что повторные чтения одного адреса сильно искажаются кэшированием. Уникальные LBA №008 уменьшают эту проблему, но **не исключают Windows/USB/HDD кэш, read-ahead, планировщик, вращение шпинделя, радиальное положение**. Отдельные режимы используют немного разные адреса. Не выдавать наблюдаемые задержки за чистое время seek, карту реальных дорожек, ускорение «Зебры» или повышение ресурса.

## Как интерпретировать

Сопоставить все три раунда, стабильность относительных различий, хвосты p95/p99 и подозрительно короткие чтения. Положительный, отрицательный или неопределённый результат равно допустим. Если упорядоченный доступ окажется быстрее, это доказательство только в контексте данного стенда, а не тест Adaptive Macro Interleave: для последнего нужны два реально реализованных варианта файловой раскладки и отдельное разрешение на операции записи на тестовом носителе.

Связи: №003 — стоимость отдельного перехода; №005 — влияние повторного чтения/кэша; №007 — карта NTFS не равна магнитной геометрии; №008 — цена длинной последовательности обращений.
