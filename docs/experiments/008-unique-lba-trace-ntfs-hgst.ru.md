# Опыт №008 — цена длинной последовательности чтений по новым LBA (HGST T:, NTFS)

**Состояние:** **ФИЗИЧЕСКИЙ ОПЫТ ПРОВЕДЁН 13.11.2026** на HGST T: NTFS, подтверждён успешным консольным журналом пользователя. Все 44 unit-теста прошли. Первичные CSV/JSON пока находятся на Acer, их числовое содержимое ещё не получено в GitHub — **ускорение и разность времён НЕ вычислены**. Продолжение №003 без повтора №003/005: другой объект исследования — суммарная цена длинной последовательности.

## Система, файловая система и границы

- Физический **2,5-дюймовый HDD HGST HTS725050B7E630**, Windows **Disk 2**, том **T: / NTFS** (существующий рабочий том, не переписывается).
- ORICO / VIA Labs `2109:0715`, USB SuperSpeed 5 Гбит/с и UAS — проверенное ранее аппаратное подключение, но перед опытом идентификаторы подлежат повторной проверке.
- **НЕТ** EXT4, Linux, дефрагментации, создания 1-ГиБ файлов, переноса экстентов или изменения NTFS. Метаданные `VCN/LCN` здесь не измеряются — это отдельный опыт №007.
- Чтение `\\.\PhysicalDrive2` по 4 КиБ, адреса от примерно 5% до 95% логического пространства, выравнивание 4096 Б; все адреса в рамках одного опыта неповторяющиеся.

## Отличие от 003 и 005

№003 сравнивал одиночные near/far переходы. №005 четыре раза перечитывал одни и те же адреса, что явно выявило кэширование. №008 сравнивает **суммарную задержку и сумма длин переходов** в длинных последовательностях новых адресов, пространственно сгруппированных и перемешанных.

Для ослабления эффекта перекрёстного прогрева два режима используют **разные, но стратифицированные по радиальным диапазонам адресные множества**. Поэтому эффект порядка нельзя считать идеально изолированным: распределения примерно сопоставимы, но фактические LBA не идентичны. Четыре трассы идут `ordered → shuffled → shuffled → ordered` (ABBA по режимам, **без повторения адресов**). Это не перенос файлов и не измерение оптимизации размещения.

## Безопасное использование

Сначала обновить проект и выполнить команды **по одной физической строке** в PowerShell:

```powershell
git pull --ff-only
uv run python -m unittest discover -s tests -v
uv run python experiment008.py
```

По умолчанию `experiment008.py` — **PLAN ONLY**: не запрашивает диски Windows, ничего не читает, не создаёт отчётных файлов и не пишет на T: или F:. По умолчанию 4 трассы по 128 уникальных адресов (512 × 4096 Б = 2 МиБ чтения). Варианты параметров ограничены 64/128/256 адресами и 4/8 трассами.

**Реальное измерение**, только после успешного прохождения тестов, подтверждения подключения именно HGST Disk 2 и проверки тома T: NTFS:

```powershell
uv run python experiment008.py --run --disk 2 --letter T --size 500106780160 --win32-size 500105249280 --bridge usb3-orico --vidpid 2109:0715 --link-speed Super --count 128 --traces 4 --seed 20261113
```

Программа проверяет модель/обе ёмкости/USB/System/Boot/Online, связь тома T: с Disk 2, **NTFS** и PnP-предка VIA Labs. Перед чтениями проверяет повторно и требует точную фразу `READ HGST DISK 2 EXP008`. **Если идентификаторы изменились — не вводить фразу, не подбирать номер диска наугад.** В случае отказа Windows не обходить права.

Результаты только на F: в `results/<UTC>-exp008-ntfs-hgst/`: `manifest.json`, `observations.csv`, `summary.csv`. Исходный NTFS-том остаётся нетронутым.

`p50/p95/p99` — задержки отдельной операции чтения, мс; сумма `abs(ΔLBA)` — **логическая**, не физическая длина движения головки.

При этих **конкретных четырёх трассах** перемешанный порядок потребовал в **1,5963 раза** больше суммарного времени (дополнительно **702,23 мс** на трассу) по сравнению с медианой упорядоченных трасс. Если относить разницу к времени перемешанного варианта, упорядоченный был на **37,35% короче по времени**. Это **описательная разница**, не точечная оценка универсального ускорения алгоритма. Сумма логических расстояний больше у shuffled примерно в **42,88 раза**. В обоих режимах одинаковые объёмы чтения, но **LBA-наборы разные**; контрольные факторы не полностью изолированы.

**Методологические ограничения:**

1. Лишь **две трассы на режим** и один seed; статистическая достоверность между независимыми опытами не оценена.
2. Каждая трасса имеет **свой** неповторяющийся набор LBA; режимы не сравнивают одни и те же адреса. Позиции стратифицированы, но не эквивалентны.
3. Первая ordered-трасса медленнее четвёртой (1332 против 1023 мс), что совместимо с прогревом/вариацией среды; **причина не установлена**.
4. `sub_1ms=0` во всех четырёх трассах; это уменьшает опасения относительно прежних субмиллисекундных повторных чтений опыта 005, но **не доказывает отсутствие кэша**.
5. Логическая сумма скачков LBA не равна пути актуатора и не позволяет рассчитать износ или сэкономленную механическую энергию.
6. Результат относится к **порядку обращений в одном USB/Windows/NTFS-стенде**, а не к созданной файловой раскладке «Гантова зебра» на NTFS. **Никакого гарантийного выигрыша или доказанного ускорения размещения данных не получено.**

Промежуточный вывод для главы 8: *«В четырёх натуральных трассах чтения по 128 новых LBA, выполненных на 2,5-дюймовом HGST через ORICO SuperSpeed, наблюдалась меньшая суммарная задержка упорядоченных адресов, чем перемешанных. Величина различия значительна в конкретном опыте, однако причинный вклад механики HDD и обобщаемый эффект файловой раскладки пока не доказаны».*

## Что будет считаться результатом

Сравнить полные суммы времён трасс, медианы отдельных обращений, сумму абсолютных LBA-переходов и разброс между двумя трассами на режим. Отмечать влияние прогрева, порядка, USB, прошивки и кэша. Не подменять сумму времени чтения расчётной геометрией пластины.

**Ограничение:** два варианта порядка чтения **не означают две реально созданные раскладки «Гантовой зебры»**. Даже если ordered окажется быстрее, это демонстрирует только эффект организации *очереди запросов*, не оптимизацию NTFS-файлов или доказательство прибавки производительности.
