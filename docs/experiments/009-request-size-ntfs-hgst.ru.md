# Эксперимент №009 — цена размера запроса, физический HGST Disk 2 / T: NTFS

**Статус 13.11.2026: ФИЗИЧЕСКИЙ ОПЫТ ПРОВЕДЁН.** Автор прислал консольный журнал успешных 180/180 реальных read-only чтений на HGST Disk 2 / T: NTFS. Первичные CSV ещё только локально на Acer; **точных скоростей и медиан в присланном журнале нет**. Не заполнять таблицы предполагаемыми числами. Продолжение натуральных испытаний для книги «Гантова зебра. Часть 2. Цена перемещения».

## Чем №009 отличается от 001–008

- **001/002/004:** профиль последовательного чтения по 16 МиБ и сравнение USB-мостов.
- **003:** изолированные пары near/far по 4 КиБ.
- **005:** влияние повторного доступа/кэша к одним и тем же LBA.
- **008:** полная стоимость длинной трассы 128 **уникальных** адресов при ordered/shuffled.
- **009 (НОВОЕ):** измерить зависимость **времени одной операции, её полезной скорости и отношения накладных расходов к размеру блока** при нескольких размерах запросов и в пяти LBA-зонах.

Условия: HGST HTS725050B7E630, физический 2,5-дюймовый HDD, Windows Disk 2, **существующий NTFS-том T:**, ORICO/VIA Labs `2109:0715` через SuperSpeed. Никакого EXT4, Linux, форматирования или размещения файлов. Чтение выполняется из `PhysicalDrive2`, а NTFS проверяется как принадлежность/тип тома; *файловой операцией по NTFS* эти запросы не являются.

## План проверки

| Параметр | Значение |
|---|---|
| Размеры запроса | **4 КиБ / 64 КиБ / 1024 КиБ (1 МиБ)** |
| Выборочные зоны | 5 / 27,5 / 50 / 72,5 / 95% LBA |
| Групп в каждой зоне | 12 |
| Запросов | 5 зон × 12 групп × 3 размера = **180** |
| Прочитанный объём | **65 520 КиБ** (63,984375 МиБ) |
| Выбор адресов | Все диапазоны выровнены по 4096 Б, взаимно не пересекаются |
| Порядок | Размеры перемешиваются внутри группы по фиксированному seed |
| Место логов | Исключительно `F:\zebra-ganta_ch2\results\` |
| Запись на HGST T: | **Запрещена / не предусмотрена** |

У всех размеров разные LBA внутри соответствующей группы, поэтому нельзя утверждать, что выбранный размер блока — единственная причина изменения скорости. Эта методика улучшает разделение от кэша, но не устраняет влияние ОС/USB/прошивки и фактического положения адреса.

## Обновление Acer — всегда до эксперимента

PowerShell 5.1, **каждая команда одной строкой**:

```powershell
Set-Location F:\zebra-ganta_ch2
git pull --ff-only origin main
uv run python -m unittest discover -s tests -v
uv run python experiment009.py
```

В конце ожидается `PLAN ONLY`. Эта команда **не обращается к устройству**. При падении хотя бы одного теста **не запускать** `--run`, сначала исправить код в GitHub и снова сделать `git pull` на Acer.

Либо для регулярного обновления после первого получения скрипта:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File F:\zebra-ganta_ch2\tools\sync-acer.ps1
```

## Физический запуск — только после проверки аппаратуры

```powershell
uv run python experiment009.py --run --disk 2 --letter T --size 500106780160 --win32-size 500105249280 --bridge usb3-orico --vidpid 2109:0715 --link-speed Super --per-zone 12 --seed 20261113
```

Программа обязана повторно проверить HGST модель, Get-Disk/Win32 размеры, `IsSystem=false`, `IsBoot=false`, `Online`, T: на **NTFS**, родителя USB VIA Labs `VID_2109&PID_0715` и затем запросить `READ HGST DISK 2 EXP009`. **Если что-то отличается — прекратить запуск**; не менять номер диска или модель без нового протокола.

На F: сохранятся `manifest.json`, `observations.csv`, `summary.csv`. В случае частичной ошибки сохраняется только доступная часть CSV и `error.txt` на F:, не на T:. Первичный `observations.csv` — обязательное основание для иллюстрации, нельзя перерисовывать предполагаемые значения.

## Для главы 4/5 книги

Исследовательский вопрос: когда рост блока делает накладные расходы малого запроса относительно менее существенными? Можно ли получить исходные данные для эвристики `B >= kTV`? **Ответ заранее неизвестен.** Реальные показатели `T` и `V` здесь не являются раздельно измеренными физическими величинами; простое сопоставление задержки и размера запроса не определяет оптимальный размер макрополосы и не доказывает ускорение адаптивной схемы. Даже возможный выигрыш крупного блока **не равен** улучшению размещения файлов NTFS.

После прогона — сначала анализ оригинальных CSV и публикация, затем принятие решения о следующем опыте. Уже завершённые 001–005 и 008 не повторять.
